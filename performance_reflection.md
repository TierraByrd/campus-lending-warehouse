# Warehouse Performance Reflection

The query plans from performance_checks.sql (saved in results/performance_checks_output.txt) show DuckDB's columnar engine skipping data the query doesn't need. In Check 1, counting loans by category only needed to know which item each loan was for, and the scan on fact_loans lists a single projection, item_key. The other seven columns were never read. A row-based database would have pulled every full row off disk just to get that one value. Check 2 did the same thing, reading only date_key and campus_key from the fact table. The plans also show DuckDB compressing values (the internal_compress steps) before the join and group by. That's a separate benefit from skipping columns, since it makes the values it does read smaller to work with in memory.

The star schema kept every query simple. Each question only joins the fact table to the dimensions it needs. Query 2 joins one dimension, Query 6 joins three, and Query 5 doesn't need any because the flags are right on the fact row. There's never a chain of joins to get to one piece of information like there would be in a normalized design. Filtering adds to that. In Check 2, the Fall 2026 filter shows up inside the dim_date scan itself, so only about 7 of the 26 dates moved on to the join, and fact rows from other semesters were thrown out right at the join instead of being carried through the whole query. Partitioning would push this one step further. If fact_loans were stored as Parquet files split by year, a query for 2026 could skip the 2025 files completely without opening them, the same way the January 2026 query in my Week 4 project only scanned 1 of 4 files.

For the dashboard side, DuckDB doesn't have true materialized views, so Check 3 uses a summary table built with CREATE TABLE AS SELECT. The join and group by for loans per month and category runs once, and a dashboard asking about September 2026 reads the summary table with no joins at all. With this sample data it's 27 summary rows against 32 fact rows, so the savings are small here. At real scale the gap gets big. A few years of loans could be hundreds of thousands of fact rows, while the summary table stays at one row per month and category. The trade-off is the summary table has to be rebuilt when new loans come in, which is what a materialized view would handle on its own in a warehouse like Snowflake.
